# 本地资源发送耗时核查（网页 0.0.107）

## 复现环境与范围

- Windows，本机 `127.0.0.1:3006`，Next.js 生产构建，Chrome HTTP/1.1；地球附近视角、TDB `847420778.1826147`、暂停、视场角 45°。浏览器使用新测试会话；本地文件与系统磁盘缓存均已预热。
- 浏览器 Resource Timing 和 CDP 区分请求启动前等待、响应头等待、响应体接收；失败/取消的请求不计入成功请求的统计。不能把请求启动前等待一律归因于服务端，也不能以单次场景统计代表全部设备。

## 根因与对照

- 地球贴图 `color_512_4.png`（395645 字节）本地 `readFile` 加 SHA-256 核验约 0.4–1.8ms；旧 Next App Router 路由新建连接时，curl 响应头约 8–11ms，完整响应约 312–324ms。
- 同机最小 Node HTTP 服务用 `res.end(bytes)`，完整响应约 8ms；先调用 `flushHeaders()` 再发送相同数据，完整响应约 313ms。旧版 Next 的 Web Response 到 Node 响应桥接会先 `flushHeaders()`；该对照只证明本机发送方式相关，不宣称已确定 Windows TCP 内部原因或其他系统均有同样延迟。
- 新路径保留原 App Route 的资源获取、白名单、散列校验、状态和缓存头，以 Pages API 的 Node 响应一次发送已准备好的有界二进制内容。五次全新 curl 连接：地球贴图 9.8–22.4ms；银河瓦片（540816 字节）14.3–28.4ms。服务器进程已预热、不同请求时间不可直接推断首次上游成本。
- 地球面、土星环、银河瓦片、恒星文件以及未知路径的新旧响应对比：状态、字节 SHA-256、长度、类型、缓存头和 ETag 一致；HEAD、404、压缩请求和近景场景鼠标操作进行了检查。恒星文件服务器内存缓存冷启动时仍需访问 NASA，本次一次实测 473ms，缓存命中约 7ms。

## 场景验证与未解决问题

- 两次独立 Chrome 场景记录均完成 48 张行星面、68 个银河资源及 106 个成功 DYN 请求，真实画面中地球、卫星和轨迹正常。浏览器帧内排队和加载量受资源缓存、网络和 GPU 状态影响，前后两次不足以证明整体启动耗时或平均帧率改善。
- 修改后场景内 DYN 请求平均约 694ms，其中浏览器发出请求前约 539ms、响应头等待约 155ms；仍有个别银河文件响应体约 300ms。Chrome 观察到三次约 3 秒主线程长任务；具体任务来源和剩余传输停顿尚未定位。禁止通过减少对象、缩短轨迹或降低画质来掩盖这些问题。
- 内存、GPU 耗时与显存未做同条件前后量化；多浏览器争用 GPU 时曾测到更长的编译等待，已关闭本任务的额外测试实例后重新验证。NASA Eyes 在线全场景对标未在本次完成。
