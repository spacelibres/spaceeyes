## 1. 架构目标与决策状态

太空之眼以一个 Rust 编写并编译为 WASM 的核心引擎承载三维渲染与通用仿真运行机制。平台通过统一插件契约扩展业务，插件以市场方式分发、安装和管理。大模型作为插件能力接入，同样遵守平台权限和核心接口边界。

平台领域覆盖天文学与多天体三维仿真，包括恒星、行星、天然卫星、小天体、行星系统、星系及天文观测，也可扩展至航天器和人造卫星。地球只是可加载的一个天体，人造卫星只是一个对象类别；核心不得以它们作为默认中心或限定平台范围。领域覆盖是架构目标，具体物理模型、数据完备性与精度由各插件规格分别定义。

### 1.1 用户已确定的原则

- Rust 主要用于核心引擎，面向浏览器编译为 WASM。
- 核心之外的业务功能均以插件方式扩展。
- 插件采用 TypeScript，平台及插件界面的集成采用 Next.js 与 React 技术体系。
- 插件通过插件市场发现、分发和管理。
- 平台嵌入大模型能力，所有扩展围绕同一个核心及其边界工作。
- 大模型能够根据用户需求自行编写插件，生成的插件必须在平台提供的公开接口和授权范围内运行。
- 所有公开 SDK 能力必须配套版本化技能书，明确可做、不可做、开发流程和验收条件；模型开发插件必须遵循对应技能书。
- 插件必须服务于太空之眼核心支撑的三维场景、仿真、数据、分析和交互任务；平台不是通用应用或任意插件生成器。
- 当前只编写架构规划，不进入引擎或插件实现阶段。

### 1.2 本稿提出、尚待审定的设计

采用“单核心、稳定协议、受控宿主、分级隔离、插件市场”的结构。市场负责分发和治理，运行时负责加载和约束，两者分别演进。

首期建议以浏览器单机交互为主，采用平台运营方审核发布的市场；未来允许接入经组织授权的私有插件源。多人协同、商业结算和远程大规模计算保留扩展位置，不作为首期交付承诺。

## 2. 系统边界

### 2.1 核心引擎的职责

| 模块 | 负责内容 | 边界 |
| --- | --- | --- |
| 渲染内核 | 相机、渲染调度、拾取、基础几何与材质、GPU 资源 | 不嵌入卫星、行业图层等业务规则 |
| 场景状态 | 实体标识、变换、可见性、对象关系、资源引用 | 状态由命令修改，不暴露任意内存写入 |
| 空间基础 | 分层参考系、多尺度精度、局部原点、通用变换 | 不固定地球中心、地球半径或单一天体模型 |
| 仿真时钟 | 播放、暂停、步进、倍速、固定逻辑时间 | 不实现具体轨道、传感器或任务算法 |
| 通用调度 | 更新阶段、任务预算、结果应用顺序 | 业务计算由插件提供 |
| 资源管理 | 句柄、引用、释放、资源配额和所有权 | 不承担数据源认证或市场下载 |
| 核心接口 | 命令校验、查询、事件、能力发现 | 不依赖 Next.js、插件包或模型供应商 |

核心可以提供内置基础渲染能力。新的业务显示方式优先组合已有图元、材质和数据接口；确实需要新渲染原语时，通过核心版本演进增加能力，不能让插件任意注入核心代码。

### 2.2 平台宿主的职责

宿主属于必要的平台基础设施，负责启动 WASM、画布挂载、插件运行时、权限代理、界面扩展槽、项目存储和市场客户端。认证、审计、密钥代理及组织策略由平台服务提供。

“其它一切插件化”指业务扩展必须插件化；安全边界、引擎启动和插件管理不能依赖某个第三方插件才能成立。内置市场页面可使用与业务插件一致的界面扩展方式，但安装器和权限执行器属于宿主。

### 2.3 插件的职责

天体目录、星历、恒星与行星系统、天然卫星与小天体、各天体表面和大气、天体运动与物理模型、天文观测、航天器与人造卫星、载荷与传感器、数据接入、分析、报告及大模型助手均属于插件领域。官方插件与第三方插件遵守相同接口；官方身份不自动扩大权限。

天体模型使用通用身份、形状与尺度、姿态、参考系、时间相关状态和数据来源进行描述；不同天体可提供不同的表面、大气、环系或物理属性，不要求都具有地球式地形和经纬度。地理信息能力只在适用天体和参考系下启用。

## 3. 技术分层与依赖方向

| 层级 | 技术与形态 | 对外接口 |
| --- | --- | --- |
| 核心 | Rust → WASM | 版本化核心协议 |
| 桥接 | TypeScript SDK + WASM 绑定 | 类型化命令、查询、事件和资源接口 |
| 浏览器宿主 | Next.js 客户端区域 + React | 插件生命周期与界面扩展槽 |
| 平台服务 | Next.js 服务端接口及按需独立后台服务 | 身份、市场、存储、模型代理和任务接口 |
| 插件 | TS 模块、Worker、隔离界面 | SDK 与经过授权的服务代理 |
| 市场 | 元数据服务、制品存储、审核发布流程 | 检索、版本解析、下载、撤销和更新 |

依赖方向为：插件 → SDK → 宿主代理 → 核心协议 → Rust 核心。市场管理制品，不直接驱动渲染。核心不得反向依赖某个插件或其服务端。

Next.js 承载平台应用。插件界面使用 React 和 TS，在 Next.js 宿主提供的槽位中展示；隔离插件运行自己的静态界面。第三方市场包不能把任意 Next.js 服务端路由安装进平台进程。

需要服务端计算的插件可以调用已审核的平台能力，或声明外部 HTTPS 服务。自托管组织若要部署插件配套服务，必须走单独的部署和运维审批，不能随用户点击安装自动执行。

## 4. 核心与插件契约

### 4.1 接口类别

| 类别 | 用途 | 约束 |
| --- | --- | --- |
| Command | 创建对象、修改属性、控制时钟 | 参数校验、权限校验、结果确认 |
| Query | 查询场景、能力、任务状态 | 按项目和资源范围过滤 |
| Event | 订阅变化、选择、时间和错误 | 有订阅配额、顺序语义与取消机制 |
| Resource | 上传几何、纹理和批量数据 | 句柄化、配额化、明确所有权 |
| UI contribution | 注册面板、菜单、工具栏、属性编辑器 | 使用宿主指定槽位与生命周期 |
| Tool contribution | 注册供模型调用的工具 | 声明参数模式、权限和副作用 |

公开契约独立于 WASM 内部内存布局。核心协议版本、SDK 版本、宿主版本与插件版本分别维护，通过兼容范围和能力发现协商，不要求所有组件同步升级。

### 4.2 命令与事件语义

命令携带协议版本、请求标识、项目标识、操作和参数。插件身份与授权范围由宿主根据运行实例注入，不能相信插件自行填写的身份。

宿主先验证权限、配额和数据结构，核心再验证对象状态及核心不变量。命令返回成功结果或结构化错误；异步任务返回任务句柄，不将“已接受”解释为“已完成”。

同一项目内的状态写入由宿主安排顺序。批量操作明确选择原子提交或逐项结果，禁止部分成功却返回整体成功。事件携带序列信息；断线或事件丢失时通过快照重新同步。

错误至少区分：参数无效、权限不足、能力不支持、版本不兼容、资源不足、任务取消、运行失败。可重试错误必须标明条件，写入操作重试使用幂等标识。

### 4.3 高频数据与时间

逐帧数据使用批量数组和资源句柄传递，避免每个对象、每帧单独调用。批量数据须定义格式版本、字节序、字段布局、单位与时间基准。共享内存只能作为后续优化，基础契约不得依赖其存在。

渲染帧与仿真步进分离。插件按声明的采样步长计算结果，宿主将结果按仿真时间提交，不能让模型网络请求阻塞渲染循环。迟到结果按任务策略丢弃、暂停等待或重算，并记录状态。

场景持久化使用高精度坐标及明确参考系，渲染采用局部原点策略。单位、参考系、历元和时间尺度必须显式记录。具体天体坐标转换由领域插件提供，但公共数据结构由平台统一约束。

空间框架支持星系、恒星系统、天体中心、天体固连和局部区域等层级，不能要求所有对象长期使用同一组全局浮点坐标。核心负责层级关系、变换组合与渲染精度策略，领域插件提供相应参考系的物理定义和随时间变化的变换。跨尺度切换使用分层表示与细节调度；星系尺度和表面细节的共同展示不等于同一物理求解器能够处理全部尺度。

观测展示应区分天体在指定时刻的状态与观测者接收到的表观位置。光行时、参考系转换、星历插值和时间尺度转换由声明支持这些能力的插件提供，界面标明计算模式与有效范围，不能把普通几何视图默认为精确天文观测结果。

## 5. 插件包规范

每个插件发布为不可变制品，具有全局标识、作者标识、版本和内容摘要。入口仅允许引用包内经过验证的文件；外部网络能力必须单独声明。

| 清单字段 | 含义 |
| --- | --- |
| id / publisher / version | 插件身份、发布者和语义化版本 |
| hostRange / sdkRange / protocolRange | 宿主、SDK、核心协议的兼容范围 |
| requiredCapabilities | 必需核心或宿主能力 |
| entries / runtimeClass | UI、Worker 等入口及运行隔离类别 |
| permissions | 所需能力、资源范围、网络域名 |
| contributions | 面板、命令、数据源、仿真模型及模型工具 |
| dependencies | 依赖插件标识和版本范围 |
| dataSchemaVersion | 插件持久化数据格式版本 |
| migrations | 已声明的数据迁移入口与适用版本 |
| integrity / signature | 制品摘要、签名及验证所需信息 |
| license / privacy / support | 许可、数据使用说明和支持信息 |

清单定义属于本稿的规范方向；具体字段类型和 JSON Schema 在插件契约设计阶段冻结。

插件安装锁定精确版本与摘要，运行时不得自动解析成另一个版本。同一插件首期每个项目只激活一个版本；依赖图不得有循环或不兼容版本冲突。

## 6. 插件运行时与隔离

### 6.1 运行类别

| 类别 | 运行位置 | 适用范围 |
| --- | --- | --- |
| 受信任界面插件 | 宿主 React 扩展槽 | 通过运营方审核、允许进入同一执行环境的插件 |
| 隔离界面插件 | 独立来源的 sandbox iframe | 默认第三方界面插件 |
| 计算插件 | 独立 Worker | TS 仿真计算、解析和批量处理 |
| 外部服务集成 | 受控网络代理或独立服务接口 | 数据源、模型及后台计算 |

Worker 提供任务隔离和终止能力，本身不是完整权限沙箱。不得仅凭使用 Worker 就认定插件无法联网或访问浏览器能力。执行来源、网络策略、跨来源消息校验和代理授权需共同构成边界；不满足限制条件的制品不得按隔离等级发布。

同一 React 执行环境的插件拥有更高信任要求。平台不声称可以在同一 JavaScript 环境中完全约束恶意插件；审核未通过的包必须隔离运行。

### 6.2 生命周期

发现 → 下载 → 校验 → 安装 → 授权 → 启用 → 激活 → 停用 → 卸载。

更新、迁移失败、隔离崩溃和撤销分别进入明确状态。安装完成不代表默认启用，启用不代表所有权限自动获批。

激活时注册贡献点；停用时撤销订阅、取消任务、注销工具并释放所属资源。插件崩溃后宿主可终止其隔离环境；同环境插件只能提供较弱的故障隔离保证。场景数据按所有权策略保留或转为不可执行占位对象，不能静默丢弃。

### 6.3 权限模型

权限按能力与范围授予，例如当前项目场景读写、数据源域名、指定文件、模型调用和外部服务访问。宿主维护授权记录，插件只能调用获得的能力句柄。

新增权限或扩大网络范围的更新必须重新授权。撤销授权应即时阻止新请求，取消可取消任务，并记录不能撤回的既有外部副作用。

## 7. 插件市场架构

### 7.1 市场组成

| 子系统 | 职责 |
| --- | --- |
| 目录与搜索 | 分类、介绍、版本列表、兼容条件和审核状态 |
| 发布者管理 | 发布者身份、命名空间、签名信息和权限 |
| 发布流水线 | 制品上传、结构验证、安全检测、兼容验证与审核 |
| 制品仓库 | 不可变包、摘要、签名和分发 |
| 安装解析器 | 依赖解析、兼容判断、精确版本锁定 |
| 生命周期管理 | 更新、灰度、回滚、停用、撤销和审计 |
| 治理与反馈 | 举报、弃用、漏洞响应、发布者处置 |

市场首先是分发与治理体系，是否收费不改变插件接口。付费、订阅、分账及退款属于后续商业决策，不纳入首期协议。

### 7.2 发布与安装流程

发布者提交清单和包 → 自动校验 → 兼容与行为检查 → 审核 → 签名发布 → 市场可见。签名用于验证来源及完整性，不代替安全审核。

用户选择插件 → 解析兼容版本与依赖 → 展示权限和数据流向 → 验证下载制品 → 记录精确版本 → 获取授权 → 安装启用。失败时恢复安装前状态，不留下半激活的依赖图。

发布后的同一版本制品不得替换。修复必须发布新版本；下架与撤销保留版本记录和审计信息。

### 7.3 更新和回滚

默认不在正在运行的仿真中热更新。更新前保存项目快照、锁文件及插件数据备份，完成兼容检查后在安全时点切换。

迁移先在副本上执行，校验通过才提交。代码回滚不等于数据回滚：不支持逆向迁移时恢复更新前快照，禁止用旧插件直接读取新格式数据。

紧急撤销阻止新安装，并按组织策略停用已安装版本。离线环境使用缓存的撤销信息，不能承诺即时获知远端撤销；重新连接后先同步治理状态。

### 7.4 市场部署选项

建议先采用平台统一市场、受审核发布者和单一官方源，降低协议尚未稳定时的兼容成本。组织私有市场作为后续能力，复用制品格式、签名验证和安装协议。任意第三方源暂不开放，避免首期同时引入多源信任与命名冲突。

## 8. 大模型嵌入架构

模型助手是插件，通过宿主工具注册表发现获授权的能力。模型供应商适配属于 TS 服务端集成，核心不依赖任何供应商 SDK。

调用链为：用户意图 → 模型生成结构化调用 → 宿主校验身份、参数、项目范围与权限 → 插件或核心执行 → 返回结果与审计标识。

模型输出属于不可信输入。场景写入、文件导出、外部发送等操作按影响等级执行预览或确认；用户授权范围不能由模型自行扩大。来自插件说明、数据文件和模型上下文的文本不能授予权限。

密钥保存在服务端或组织密钥系统，不进入插件包、浏览器持久化及项目导出。向模型发送的场景信息按最小必要范围提取，敏感数据须受组织策略约束。

长任务采用异步任务句柄，支持进度、取消、超时、预算与限流。模型不可直接访问 WASM 内存、执行任意宿主代码或绕过安装器安装插件。生成、验证、安装和启用均通过宿主提供的受控接口进行。

### 8.1 模型自主编写插件

大模型同时具有使用插件和开发插件两类能力。用户提出需求后，模型必须先选择并读取对应版本的 SDK 技能书、类型定义、插件模板与示例，编写 TS 逻辑及 React 界面，生成完整插件包，再根据验证结果自行修正。技能书是开发入口和规范依据，不能由模型自行选择忽略。

平台公开的插件契约是能力边界。模型只能组合平台已开放的能力；需求超出接口时，应报告缺少的能力并提出接口扩展建议，不能修改 Rust 核心、WASM 绑定、宿主内部代码、权限执行器或市场审核规则来实现绕过。

模型生成的插件与人工开发的市场插件遵守相同清单、版本、权限、资源预算和生命周期规范，不设模型专用特权通道。模型可以在用户预先授予的范围内自动完成开发闭环，无须每次编辑都请求确认；新增权限和公开发布仍按宿主策略处理。

### 8.2 插件生成与验证链路

需求 → 检查是否属于平台领域 → 匹配并读取版本化技能书与已有插件 → 制定插件能力和权限清单 → 在独立工作区生成源码 → 类型及依赖检查 → 契约与权限检查 → 隔离构建 → 沙箱运行验证 → 生成不可变制品 → 经安装器安装到项目 → 启用并观察运行结果。

| 阶段 | 必须满足的条件 | 失败处理 |
| --- | --- | --- |
| 能力规划 | 需求可以映射到已公开接口，权限不超出授权范围 | 报告能力缺口或请求必要授权 |
| 源码生成 | 只使用公开 SDK、允许的依赖和声明入口 | 返回诊断，由模型修正 |
| 构建 | 独立执行环境、无平台凭证、依赖锁定 | 超时终止，保留构建诊断 |
| 验证 | 类型、契约、权限负向测试和生命周期验证通过 | 限次修复，失败后不启用 |
| 项目安装 | 制品摘要、兼容范围、权限和资源预算通过校验 | 恢复原项目状态 |
| 市场发布 | 发布者身份和市场审核流程通过 | 保持为项目内私有插件 |

生成工作区与平台源码、宿主进程及生产密钥隔离。构建脚本也属于不可信代码；依赖获取通过受控来源完成，默认不执行任意依赖生命周期脚本。运行时限制由宿主代理、隔离环境及网络策略执行，不能只依赖提示词、类型检查或源码扫描。

默认先生成项目内私有插件。模型可以通过受控接口提出安装、更新或发布请求，但模型生成成功不等于获准执行，项目安装也不等于公开发布。公开进入市场必须走与其它发布者相同的治理流程。

### 8.3 闭环修复与可追溯性

平台向模型提供脱敏的编译诊断、测试结果、资源指标与运行错误。模型可在既定次数、时间和费用预算内修改插件并重新验证；修复产生新版本，禁止原地替换已安装制品。

每次生成记录用户需求、接口版本、源码版本、依赖锁文件、验证报告、制品摘要和授权范围。更新失败沿用插件市场的快照与迁移回滚规则；运行异常时停止相关插件并释放资源。

典型场景：用户要求“展示木星及其天然卫星随时间的运动，并添加观测视角面板”，模型先匹配天体目录、星历、参考系、场景、时间及界面技能书；接口齐备时生成插件、验证并在授权项目内启用。若需求进一步要求精确表观位置，而平台缺少相应光行时或观测计算能力，则明确说明能力缺口，不把几何展示冒充精确观测结果。

### 8.4 SDK 技能书体系

每项公开 SDK 能力都必须具有对应技能书。技能书以 `SKILL.md` 为入口，可附带接口 Schema、TS 类型引用、模板、示例和可执行验证规则。技能书描述如何正确使用真实 SDK，不能替代接口实现、类型定义和运行时权限检查。

技能体系采用“平台总规范 → 领域技能书 → 接口与验证资源”的结构。总规范定义核心边界、通用生命周期、权限和禁止事项；领域技能书分别覆盖场景、时间、数据、分析、界面及模型工具等能力。模型按任务加载相关技能及依赖，不把整套能力无差别加入每次任务。

| 技能书内容 | 必须明确的规范 |
| --- | --- |
| 身份与版本 | 技能标识、适配 SDK 与协议版本、依赖技能 |
| 适用范围 | 解决的平台任务、触发条件及不适用场景 |
| 允许能力 | 可调用接口、参数、单位、参考系与返回结果 |
| 禁止行为 | 禁用接口、内部模块访问、越权及领域外开发 |
| 权限与预算 | 最小授权、网络范围、资源与执行限制 |
| 开发步骤 | 输入检查、生成、构建、验证、安装和清理流程 |
| 数据与错误 | 数据归属、迁移、错误处理和恢复要求 |
| 示例与反例 | 合规用法、违规用法及其原因 |
| 验收规则 | 可执行契约测试、权限负向测试和领域结果验证 |

SDK 与技能书作为配套能力包发布，记录精确版本及内容摘要。发布流程检查技能书中的接口是否存在、示例是否符合类型约束、验证规则是否可执行；接口变更必须同步更新技能书。缺少技能书或版本不兼容的能力不向模型开发流程开放。

已安装插件记录生成时采用的技能版本。技能升级不自动改变既有插件行为；插件更新时重新检查兼容性与规则。紧急安全规则可由宿主策略立即执行，不能等待模型重新阅读文档。

### 8.5 领域约束与规范执行

所有允许的插件类型都应能够通过大模型完成开发流程，但其具体功能必须能够映射到已发布 SDK 和技能书。此目标不意味着模型可以超出现有能力实现任意需求，也不意味着无需领域验证即可保证算法正确。

| 需求类别 | 处理方式 |
| --- | --- |
| 平台领域内且已有能力覆盖 | 按对应技能书自动开发和验证 |
| 平台领域内但缺少接口或技能 | 输出能力缺口及扩展建议，等待平台维护者补充规范 |
| 与平台核心无关 | 说明不属于插件范围，不生成无关应用 |
| 需要越权或访问内部实现 | 拒绝该实现路径，检查是否存在合规替代接口 |

领域相关性必须体现在插件声明的能力、贡献点和核心资源关系中。例如星图、行星系统演化、各天体表面展示、食与掩星分析、观测视角、轨道可视化、仿真数据导入和结果报告属于平台任务；通用商城、社交应用或与天文学及仿真无关的网站生成不属于插件目标。仅仅声明使用一个场景接口，不能成为开发无关业务的理由。领域约束不得误写成只允许地球与人造卫星功能。

规范采用三层约束：技能书指导生成，构建与验收规则检查制品，宿主权限与隔离环境约束实际执行。自然语言条款中不能自动判定的部分保留人工审核，不能将通过静态扫描等同于完全合规。

插件包附带能力映射与验证报告，记录采用的技能、接口和权限。项目启用需通过基础验证；公开市场发布还需领域范围和市场治理审核。模型生成的说明、插件自述及外部文档不得覆盖平台技能书与宿主策略。

## 9. 数据与项目持久化

项目由核心场景快照、资源引用、插件锁文件、插件独立命名空间数据及仿真配置组成。模型密钥、登录凭证和可执行插件包不直接嵌入项目文件。

项目打开时先检查格式、插件依赖、精确版本和能力条件，再恢复核心状态及插件数据。缺失插件的对象显示不可执行占位信息，保留原始数据，并提示安装依赖或导出处理。

插件数据只通过其命名空间访问，跨插件共享必须使用显式契约与授权。外部资源记录来源、内容摘要、许可和缓存策略；离线项目只承诺可使用已缓存且许可允许的数据。

首期不承诺跨设备逐位一致的物理结果。需要可复现实验时，记录输入、插件版本、初始时间、随机种子和逻辑步长，并由领域插件声明精度与复现范围。

## 10. 性能、兼容与故障策略

GPU 后端、浏览器最低版本和回退策略通过技术验证后冻结，不在架构草案中指定未经验证的库版本。

性能验证覆盖对象规模、渲染帧时间、仿真步耗时、插件通信开销、首屏加载、内存与显存资源。具体目标在目标设备和典型场景确定后制定，不能以脱离硬件的帧率作为验收指标。

资源按插件归属计量，超额时拒绝分配、降采样或终止对应任务。核心记录资源所有者，插件卸载后可以回收遗留句柄。

设备丢失或核心崩溃时，宿主停止写入，从最近有效快照恢复，并提示未持久化操作。单个插件失败应尽量限制在其运行环境内；关键依赖失效时暂停相关仿真，不能继续输出看似有效的结果。

## 11. 工程组织与验证

建议使用单仓库管理核心、宿主和 SDK，官方插件可在首期同仓开发，但仍产出独立制品。第三方插件只依赖公开 SDK 与规范，不能导入宿主内部源码。

| 建议目录 | 内容 |
| --- | --- |
| crates/engine | Rust 核心与内部模块 |
| crates/wasm-bridge | WASM 导出适配 |
| packages/protocol | 跨语言协议定义与生成输入 |
| packages/plugin-sdk | TS 插件 SDK |
| skills | 与 SDK 配套的版本化技能书、模板及验证资源 |
| packages/plugin-runtime | 宿主代理、权限与生命周期 |
| apps/platform | Next.js 平台与市场客户端 |

上述为规划目录，本阶段不创建实现脚手架。协议只保留一个权威定义源，生成两侧类型并在持续集成中检查漂移。

验证分为核心单元验证、WASM 浏览器验证、SDK 契约验证、插件兼容验证、权限隔离验证、市场升级回滚验证和完整业务闭环验证。第三方制品必须经过版本矩阵与权限负向测试后才可发布。

平台界面及后续品牌文档遵守 spacelibre 视觉规范，使用版本化源中的正式 logo；本文为纯文本架构规范，不新增视觉资产。

## 14. 2026-10-27 统一架构决策（本节优先于前文旧规划表述）

**规划阶段历史基线为0.0.0，当前统一开发版本为0.0.1。** 规划期不升版本，架构书、规则书、技术可行性方案书、代码发布版本必须一致；正式发布才按末位加一、100进1（0.0.99→0.1.0）。此前0.1.3只是历史草案编号，不代表当前正式版本。

### 产品优先级
第一阶段以 NASA Eyes 的太阳系三维探索体验为明确对标：太阳、行星、月球、真实星历、相机、轨道、时间轴、天体资料。最终最大需求是**用户用自然语言要求大模型开发插件，AI依据版本化SDK技能书自动生成、构建、测试、修复、受控安装并启用插件**。首期为最终目标预留正确SDK边界，不先实现完整AI市场。首期不做混合计算或远程GPU视频渲染。

### 核心与界面
Rust是唯一核心技术源码；WASM仅为浏览器编译目标，未来可同源码编译Native用于桌面、本机或服务器。Next.js/React/TypeScript作为统一Web界面，可通过浏览器或localhost访问。不得建设两套相互矛盾的仿真引擎。

### 模块与协议
所有模块采用模块化、面向对象的领域封装；Rust采用struct/impl/trait/组合，不强制类继承。跨模块公开结构化数据交换、跨语言/进程及持久化数据以版本化Protobuf作为唯一权威契约，内部高频数值计算可使用原生结构。未来gRPC复用Proto消息，不作为首期任务。通用核心只包含场景、时空、调度、渲染和资源机制；具体天文领域与数据接入通过受控插件扩展。

### NASA Dynamo已有技术资产
参考仓库 https://github.com/spacelibres/solarsystem 已有 src/lib/dynamo/{reader,parse,math,orbit,loader}.ts、src/solar/domain/ephemeris.ts、src/solar/runtime/explorer-runtime.ts、真实DYN测试夹具及研究文档。**禁止将DYN工作描述为从零开始**。Rust迁移必须保留五类点（orb/pos/lin/ori/quat）、分段、源索引/重复时间边界、时间与四元数语义，并以现有TS和黄金样本交叉验证。NASA原始数据、恢复源码、自研代码、第三方组件分别审查许可；未经许可核实不得直接复制恢复源码或批量分发原始数据。

### 代码审计纪律
每次代码修改必须更新CHANGELOG.md，包含原因、范围、测试、风险、关联提交；接口变更先更新MD与ADR。禁止无日志合并、无测试声称验证。AI开发插件同样适用。当前仍在规划期，本节不宣称已实现引擎或CI。


## 15. NASA Dynamo插件化决策（优先于前文DYN转换设想）

NASA Eyes DYN数据解析必须作为独立数据源插件 `spaceeyes.nasa.dynamo`，不得写入Rust Core。首期TypeScript插件复用已有解析与完整星历求值成果；在线按需获取DYN、内部直接解析，不要求预先将全部原始DYN转换为Proto文件。**公开模块交换边界仍统一使用版本化Proto**；Rust Core只接收标准化状态与场景命令。插件配套SKILL.md，为最终AI自主开发插件提供受控数据能力。详细规范见 `docs/NASA-Dynamo-插件设计规范.md`。

## 16. 最小可信插件宿主切片（2026-10-27）

## 17. 职责边界与实现语言（2026-10-28 项目负责人指令，优先于前文冲突表述）

**Rust 是唯一计算与状态权威；TypeScript/Next.js 只做交互与界面；插件市场只分发交互、皮肤与显示类扩展。** 天文、星历、时间尺度、轨道、数值计算、图像/网格/DYN/协议解码及所有核心行为测试均在 Rust 中实现。完整规范见 `docs/核心与宿主职责边界规范.md`，本节只重述不可协商的边界：

1. **Rust Core**：Scene、Time（含 UTC/TAI/TT/TDB、闰秒、J2000）、Spatial、Simulation、Resources、Rendering、Protocol、Engine；所有科学计算与解码；全部核心测试与误差对照。
2. **TS/Next.js 宿主**：DOM/React、输入、布局、主题/皮肤、格式化、网络代理、WASM 生命周期、插件 UI 容器、市场客户端；不持有权威状态、不做科学换算（仅格式化核心返回值）、不生成“科学”几何。
3. **插件市场**：面板、皮肤/主题、交互效果、命令入口、展示型图层与模型工具入口；禁止在 JS 中解码 DYN/纹理/网格、实现星历/轨道/时间算法、直接写 Scene/Clock/Resources、绕过宿主代理或扩大权限。
4. **原生能力不进市场**：数据源与算法扩展以 Rust crate + Proto 的核心版本演进交付；数据源适配器只允许“取字节 + 调用 Rust 解码/求值”。
5. **DYN 决策变更**：§15 的“TypeScript 插件运行时求值”不再作为目标架构。DYN 解析/求值/分段迁移至 Rust 核心；`packages/nasa-dynamo` 在迁移期仅作对照 oracle，浏览器运行时不得继续以 JS 科学计算为准。
6. **验收含义**：核心功能没有 Rust 测试和 GPU/数值证据不得标为完成；TS 测试只证明交互、线缆与格式化。科学结论必须附时间尺度、参考系、单位、来源与误差容限。

实施顺序与出口见 `docs/核心与宿主职责边界规范.md` 第 7 节及 `docs/全设计要求实现与集中验收台账.md`。
